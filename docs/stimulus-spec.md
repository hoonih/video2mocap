# 자극 영상 사양 (Stimulus Spec)

SignPost팀 IRB 승인 연구용 자극 영상(조건 A 원본 / B 골격 / C 3D 아바타)의 제작 사양.
이 문서의 값이 바뀌면 이미 생성된 자극 66개를 전부 다시 만들어야 한다.

결정일: 2026-10-24 (Phase 0)

## 1. 출력 사양 (A·B·C 공통, 변경 금지)

| 항목 | 값 | 근거 |
|---|---|---|
| 해상도 | **720×1280 (세로 9:16)** | 참여자 다수가 스마트폰 세로 화면으로 시청. H.264 level 3.1 한도(1280×720급) 안에 들어감 |
| fps | **30 (CFR, 고정 프레임레이트)** | 원본 촬영 fps와 동일. 스마트폰의 가변 프레임레이트(VFR)는 30 CFR로 정규화 |
| 프레임 수 | 같은 문장의 A·B·C가 **정확히 동일** | 길이 차이는 교란변인 |
| 화자 크기 | 어깨너비 중앙값 기준 자동 줌으로 통일 (Phase 3) | 촬영 거리 차이 보정 |
| 코덱 | H.264 (libx264), `yuv420p`, profile baseline, level 3.1 | iOS Safari / Android Chrome 재생 (Phase 4) |
| 기타 | `-movflags +faststart`, 오디오 없음(`-an`) | 모바일 스트리밍, 청각장애인 대상 연구 |

## 2. 표현 모드

- **상체 모드 고정**: 모든 자극에 `--upper-body` 적용. 수어는 상체 중심.
- **다리 숨김 기본값**: 상체 모드에서 합성 하체를 그리지 않는다 (Phase 8-4를 기본 동작으로).
- 조건 B·C는 같은 카메라 파라미터(거리, 높이, 초점거리, yaw)와 배경색을 공유한다.
- 조건 B·C에는 원본 픽셀이 한 프레임도 들어가지 않는다.
- 비수지 신호(눈썹, 입 모양, 머리 회전)는 B·C 모두에 표현한다.

### 비수지 신호 표현 (Phase 1, 2026-10-24 결정)

- 표현 요소: 눈썹(좌우 각 5점 폴리라인), 눈(4점 폴리곤), 코끝, 입(4점 폴리곤, 벌림 정도),
  머리 회전(yaw/pitch/roll — 얼굴 요소가 머리 구 위에서 이동하고 먼 쪽 요소는 가려짐)
- **표정 움직임은 실측 그대로** 쓴다. 눈썹·입 변위를 증폭하지 않는다 (B·C가 A보다 비수지를
  강하게 보여 주는 교란을 피하기 위함).
- ~~머리·얼굴 확대 배율 1.4~~ → **2026-10-25 1.0으로 되돌림** (아래 Phase 4B 참고). 당시 결정:
  머리·얼굴 확대 배율 1.4. 머리 중심 기준으로 머리 구와 얼굴 요소를
  함께 키워 화면상 변화량만 늘린다. 720×1280에서 머리 반지름 86px → 약 120px.
  - 근거: 배율 1.0에서는 일반적인 눈썹 움직임(5~10mm)이 화면에서 4~9px에 그쳐 구분이 어렵다.
  - 부작용: 손이 닿는 얼굴 위치(턱/입/볼/이마)가 원본과 어긋날 수 있다. Phase 10 수어 사용자
    검수에서 위치가 의미를 가르는 문항을 별도로 확인한다.
- 얼굴 크기는 화자 실측이 아니라 표준 얼굴(눈꼬리 간 8.9cm)로 정규화한다.
- 미검증: 실제 눈썹 올림/내림 촬영본으로 아직 검증하지 않았다. 샘플 영상(`input2.mp4`)에는
  눈썹 올림/내림 구간이 없다 (정면 프레임 기준 최대 변화 3.9mm).

### 조건 B 골격 표현 (Phase 2)

- `--view skeleton` (`SkeletonRenderer`): 배경 위에 회색조 선과 점만. 면·바닥·그림자 없음.
- 카메라·머리·얼굴 기하는 조건 C와 같은 베이스 클래스(`_ProjectedRenderer`)에서만 계산한다.
- 얼굴: 눈썹 폴리라인, 눈·입 윤곽선(채우지 않음), 코끝 점, 머리 윤곽 원. 조건 C와 같은 가시성 규칙.
- 좌우 구분: 화자 왼쪽 부위를 약간 어둡게(0.75배).
- 조건 B·C는 같은 추적 결과(FrameData)에서 렌더링해야 한다. 같은 영상을 두 번 추적해도
  결과가 같았지만(input2.mp4, 479프레임), 배치(Phase 5)는 추적 1회 후 두 조건을 렌더링한다.

### 프레이밍 정규화 (Phase 3, 2026-10-24 결정)

- 입력은 ffmpeg로 **30fps 고정 디코딩 1회**. A·B·C가 모두 이 프레임 시퀀스에서 만들어지므로
  프레임 수가 구조적으로 같다. 프레임 수 기준은 컨테이너 메타데이터가 아니라 실제 디코딩 결과다
  (예: `input2.mp4`는 메타데이터 501, 실제 479).
- 스마트폰 회전 메타데이터(세로 촬영)를 반영해 표시 방향으로 디코딩한다.
- **조건 A도 정규화**한다: 영상마다 고정된 배율·이동 변환 1개(회전 없음, 프레임별 흔들림 없음).
  - 크기 기준: 정면에 가까운 프레임의 어깨너비(상위 90% 분위수) = 화면 폭 × 0.35.
    몸을 튼 프레임은 어깨가 좁게 찍히므로 중앙값을 쓰면 화자가 과하게 커진다.
  - 위치 기준: 어깨 중앙의 중앙값 = (화면 폭 × 0.5, 화면 높이 × 0.42).
- **조건 B·C**: 정면 프레임에서 A와 어깨너비가 같아지도록 카메라 거리를 정하고, 프레임마다 A 화면의
  어깨 중앙 위치(EMA 평활)로 옮긴다. 화자가 움직이면 B·C도 같이 움직인다. 원본 픽셀은 쓰지 않고
  추적 좌표만 쓴다.
- 상체 모드에서는 다리를 그리지 않는다 (`--show-legs`로 다시 켤 수 있음).

검증 결과 (`input2.mp4`, 같은 영상을 60%로 줄여 치우치게 놓은 `far`, 다른 구간 `other`):

| 영상 | A 정면 어깨너비/화면 폭 | A·C 어깨 중앙 차이 (중앙값/p95) | C/A 어깨너비 (정면 / 전체 p95) |
|---|---|---|---|
| input2 | 0.352 | 2.9 / 4.4 px | 1.007 / 1.236 |
| far | 0.352 | 2.5 / 4.9 px | 1.011 / 1.214 |
| other | 0.349 | 2.0 / 4.7 px | 1.016 / 1.270 |

알려진 한계:
- 몸을 크게 튼 프레임에서는 B·C의 어깨가 A보다 최대 약 25% 넓게 보인다. MediaPipe 3D 좌표가
  몸의 회전을 실제보다 작게 추정하기 때문이다.
- 빠르게 몸을 돌리는 순간 1~2프레임 동안 B·C 위치가 A보다 늦게 따라간다 (최대 약 45px, 3프레임 내 회복).

**촬영 가이드** (1080×1920 → 720×1280, 축소 배율 0.667 기준):
- 정면 어깨너비가 원본 폭의 **23~35%**(250~380px)가 되게 찍는다.
  - 35%보다 크면 축소해야 해서 조건 A 가장자리에 여백이 생긴다 (경고 출력).
  - 23%보다 작으면 원본보다 확대해야 해서 화질이 떨어진다 (경고 출력).
- 화자는 화면 가운데에 서고, 어깨가 화면 높이의 약 40% 지점에 오게 한다.

### 인코딩 (Phase 4)

- 렌더링한 프레임을 ffmpeg stdin으로 바로 넘겨 인코딩한다 (중간 파일 없음).
- 프리셋: `-c:v libx264 -pix_fmt yuv420p -profile:v baseline -level:v 3.1 -crf 23 -movflags +faststart -an`
  - 720×1280은 45×80 = 3600 매크로블록으로 level 3.1 한도와 정확히 같다. 이보다 큰 출력 크기를
    쓰면 level 3.1을 지킬 수 없다.
  - 디버그용 `side` 뷰(1440×1280)는 level을 지정하지 않으며 모바일 프리셋 검사에서 제외한다.
- ffmpeg가 없으면 설치 안내와 함께 중단한다. mp4v로 대체하지 않는다.
- 출력 직후 ffprobe로 코덱·프로파일·레벨·픽셀 포맷·오디오 유무·faststart·실제 프레임 수를 검사하고,
  하나라도 어긋나면 실패로 처리한다.
- 16초 기준 파일 크기: A 약 1.0MB, B 약 0.8MB, C 약 0.7MB.
- **배포 서버는 HTTP Range 요청(206 Partial Content)을 지원해야 한다.** iOS Safari는 Range를
  지원하지 않는 서버의 동영상을 재생하지 않는다. (Vercel, Netlify, S3, GitHub Pages는 지원.
  Python 기본 `http.server`는 지원하지 않음.)

### 얼굴 블렌드셰이프 (Phase 4B, 2026-10-25)

- 얼굴은 MediaPipe Tasks API **Face Landmarker**(VIDEO 모드)로 원본 해상도 프레임에서 추적한다.
  ARKit 호환 블렌드셰이프 51개(`_neutral` 제외)를 프레임마다 받는다. 몸·손은 Holistic 유지.
- 계수는 **증폭하지 않는다.** 다른 부위와 같은 EMA(`--smooth`)로 떨림만 줄이고, 미검출 프레임은
  직전 값을 유지한다.
- `--face-scale` 기본값을 **1.0으로 되돌렸다.** 확대는 조건 A와의 교란 요인이었다.
- 모델 파일이 없거나 Tasks API를 쓸 수 없으면 Holistic 얼굴 468점 좌표만 쓰는 기존 경로로 동작한다.
- 같은 입력이면 결과가 같다 (input2.mp4 2회 실행: JSON 동일, 출력 mp4 바이트 동일).

#### 오검출 주의 (Phase 6 QC 반영 필요)

`input.mp4`(4분, 7030프레임) 전체를 조사한 결과 (상위 극값 프레임을 눈으로 확인):

- `browInnerUp` 상위 4개 중 3개는 실제로 눈썹을 올린 프레임 (최대 0.73, 중앙값 0.15).
- `browDown` 상위 4개 중 2개만 실제로 눈썹을 내린 프레임. 나머지는 **손이 얼굴을 가린 프레임**(0.84)과
  **장면 전환으로 어두운 프레임**(0.72)이었다.
- 따라서 손이 얼굴과 겹치는 구간의 블렌드셰이프는 신뢰하기 어렵다. QC에서 손-얼굴 겹침 구간을 표시한다.

### 3D 모델 외형 (Phase 4C, 2026-10-25 결정)

- 모델: **PerfectSync 샘플 여성 모델** `VRoid_V110_Female_v1.1.3.vrm` (출처·라이선스는 `assets/avatar/README.md`).
  자극 66개 전체에 같은 모델을 쓴다.
- 원본 그대로는 눈썹이 피부색에 가깝고 앞머리에 가려 자극 크기에서 보이지 않았다. 아래 두 가지 외형 조정을
  적용한다. **표정 계수와 움직임은 건드리지 않는다.**
  - 눈썹 재질 색: sRGB `(45, 35, 30)`
  - 앞머리 숨김: 눈썹 영역(양 눈 본 바깥 2cm, 눈 본 위 1.2~6.5cm)을 머리 중심보다 3cm 이상 앞에서 가리는
    머리카락 가닥만 숨긴다 → 이 모델에서 4가닥.
    (`style: {browColor: [45,35,30], hideBangs: {margin: 0.02, browLow: 0.012, browHigh: 0.065, frontOffset: 0.03}}`)
- 확인: 자극 크기(어깨너비 35%) 렌더에서 `browInnerUp` 1.0/0.4, `browInnerUp+browOuterUp` 1.0,
  `browDown` 1.0/0.4가 모두 가려지지 않고 서로 구분된다.

| 항목 | 값 |
